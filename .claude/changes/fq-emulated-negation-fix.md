# Fq Emulated Negation Fix for Recursion Transpilation

## Overview

This document describes the work to add `FqNeg` support to the MleAst transpilation system and the ongoing investigation into why the Fq emulated assertions (a17-a20) fail verification.

## Background

The Jolt zkVM verifier has two types of field operations:
1. **Fr operations (native)**: BN254 scalar field, used in stages 1-7 (assertions a0-a16)
2. **Fq operations (emulated)**: BN254 base field, used in recursion stages (assertions a17-a20)

When transpiling to Gnark, Fq operations must use emulated field arithmetic (`fqField.Mul`, `fqField.Add`, etc.) rather than native field operations.

### Existing Infrastructure

The codebase already had partial Fq emulation support:
- `fq_mode.rs`: Thread-local `FQ_MODE` flag to toggle between Fr and Fq node generation
- `FqMul/FqAdd/FqSub` nodes in MleAst
- Operator implementations checking `is_fq_mode()` for `Add`, `Sub`, `Mul`
- Codegen generating `fqField.Mul/Add/Sub` calls
- `transpilable_verifier.rs` toggling FQ_MODE around recursion (lines 833-847)

## Architecture Analysis

### How Fq Emulation Works

The recursion verification operates over Fq (BN254 base field), but gnark circuits natively operate over Fr (BN254 scalar field). The solution is **emulated field arithmetic**.

**Real recursion verification (Rust):**
1. Transcript operates over Fr (Poseidon hash)
2. Challenges derived from transcript are used as Fq elements
3. Sumcheck polynomial evaluations computed mod Fq
4. Proof coefficients are Fq elements

**Transpiled circuit (gnark):**
1. Witness values (proof coefficients) are provided as Fr variables
2. Converted to Fq via `fqField.FromBits(api.ToBinary(x, 254)...)`
3. Poseidon hash computed natively over Fr
4. Challenges derived, then converted to Fq for emulated operations
5. Emulated `fqField.Mul/Add/Sub` used for Fq arithmetic

### Key Observation

The generated circuit (see line 11682 of `stages_circuit.go`):
```go
cse_17_814 := circuit.Recursion_Stage1_R0_0
// ...
cse_17_814_fq := fqField.FromBits(api.ToBinary(cse_17_814, 254)...)
```

The witness value `Recursion_Stage1_R0_0` is an Fq element (from the proof), but it's provided as an Fr witness variable. The `FromBits` conversion assumes the bit representation is valid for both fields.

**Potential Issue:** If an Fq value exceeds the Fr modulus, it would be reduced mod Fr when loaded as a witness, causing incorrect values.

**Modulus comparison:**
- Fr: `21888242871839275222246405745257275088548364400416034343698204186575808495617`
- Fq: `21888242871839275222246405745257275088696311157297823662689037894645226208583`

The difference is about 2^126, so most Fq values below Fr's modulus would be preserved correctly. But values in the range `[Fr_modulus, Fq_modulus)` would wrap differently.

### Remaining Hypotheses

1. **Transcript Challenge Derivation Mismatch**
   - The challenges (`cse_17_813` etc.) are derived from Poseidon hash via `Truncate128Reverse`
   - The `Truncate128Reverse` hint in Go applies:
     - 125-bit mask
     - Montgomery conversion (multiply by R^-1)
   - If the Rust symbolic execution produces different challenge values, all Fq operations would use wrong multipliers

2. **Hint-Only Challenge Computation**
   - The `Truncate128Reverse` function only uses a hint with no circuit constraints
   - The prover could provide any value (though the solver should use correct values)
   - This is a soundness issue but shouldn't cause solver failure

3. **Emulated Field Accumulation Bug**
   - The emulated field multiplications work individually
   - But when thousands are accumulated, some limb overflow/underflow might occur
   - Unlikely given gnark's mature emulated arithmetic implementation

## ROOT CAUSE IDENTIFIED (Session 3)

### The Problem

**Fq uses `Mont254BitChallenge`, not `MontU128Challenge`!**

Looking at `jolt-core/src/field/ark_bn254_fq.rs:31-33`:
```rust
// type Challenge = MontU128Challenge<ark_bn254::Fq>;
// let's test the non special 128 bit challenge
type Challenge = Mont254BitChallenge<ark_bn254::Fq>;
```

But Fr uses `MontU128Challenge` (`jolt-core/src/field/ark_bn254_fr.rs:34`):
```rust
type Challenge = MontU128Challenge<ark_bn254::Fr>;
```

### The Mismatch

**`MontU128Challenge::from(u128)` does:**
1. Apply 125-bit mask: `high = ((value >> 64) as u64) & (u64::MAX >> 3)`
2. Store as `[0, 0, low, high]` BigInt array (shifted layout)
3. Convert via `from_bigint_unchecked()` which treats input as Montgomery form → multiplies by R^-1

**`Mont254BitChallenge::from(u128)` does:**
1. Call `F::from_u128(val)` → standard field conversion
2. Uses `BigInt::new([val as u64, (val >> 64) as u64, 0, 0])` (standard layout)
3. Convert via `from_bigint()` → proper Montgomery conversion

### The Bug

The Go `Truncate128Reverse` hint implements `MontU128Challenge` semantics:
- 125-bit mask
- Montgomery R^-1 multiplication
- Shifted BigInt layout `[0, 0, low, high]`

But for **Fq operations (a17-a20)**, it should use `Mont254BitChallenge` semantics:
- No masking
- Standard `from_u128` behavior
- Standard BigInt layout `[low, high, 0, 0]`

This causes all Fq challenges to be computed incorrectly, leading to wrong sumcheck verification results.

### The Fix

1. Add `is_fq_mode()` check in `poseidon.rs::challenge_scalar_optimized`
2. When in Fq mode, generate a new `FqTruncate128` node (or `Truncate128Simple`)
3. Add the new node variant to MleAst
4. Implement Go hint for simple `from_u128` semantics
5. Update codegen to generate the new hint call

#### 4. Added Go hint (poseidon.go)

```go
func FqTruncate128(api frontend.API, x frontend.Variable) frontend.Variable {
    result, err := api.Compiler().NewHint(fqTruncate128Hint, 1, x)
    if err != nil {
        panic(err)
    }
    return result[0]
}

func fqTruncate128Hint(_ *big.Int, inputs []*big.Int, outputs []*big.Int) error {
    // Convert to 32-byte LE representation
    inputBytes := inputs[0].Bytes()
    le := make([]byte, 32)
    for i := 0; i < len(inputBytes) && i < 32; i++ {
        le[i] = inputBytes[len(inputBytes)-1-i]
    }
    // Take first 16 bytes (low 128 bits in LE format)
    le16 := le[:16]
    // Reverse bytes to match Rust challenge_u128 behavior
    for i := 0; i < 8; i++ {
        le16[i], le16[15-i] = le16[15-i], le16[i]
    }
    value128 := new(big.Int).SetBytes(le16)
    outputs[0] = value128
    return nil
}
```

## CRITICAL DISCOVERY: Fq Poseidon Uses Different Parameters! (Session 3)

### The Real Root Cause

The Rust recursion sumcheck uses `PoseidonTranscript<Fq, FqParams>` which has **completely different parameters** than the Fr Poseidon!

Looking at `jolt-core/src/transcripts/poseidon_fq_params.rs`:
```rust
pub const FQ_FULL_ROUNDS: usize = 8;
pub const FQ_PARTIAL_ROUNDS: usize = 56;
pub const FQ_ALPHA: u64 = 5;
pub const FQ_WIDTH: usize = 4;

// DIFFERENT MDS MATRIX:
pub const FQ_MDS: [[&str; 4]; 4] = [
    ["0x0c19139cb84c680a6e14116da060561765e05aa45a1c72a34f082305b61f3f52", ...],
    ...
];

// DIFFERENT ROUND CONSTANTS (256 total):
pub const FQ_ROUND_CONSTANTS: [&str; 256] = [...];
```

**But our Go circuit only has Fr Poseidon!**

When we symbolically execute the Fq recursion sumcheck, we're recording `Poseidon(...)` nodes that are supposed to be evaluated with **Fq Poseidon parameters**, but the Go circuit evaluates them with **Fr Poseidon parameters**.

### Why This Matters

The transcript challenge derivation flow:
1. **Rust (real execution)**: `PoseidonTranscript<Fq, FqParams>` hashes data over Fq field with Fq parameters
2. **Rust (symbolic execution)**: Records `Poseidon(state, n_rounds, data)` nodes
3. **Go (circuit)**: Evaluates those nodes with `poseidon.Hash()` which uses **Fr parameters**

This means EVERY hash output differs between Rust and Go, causing ALL Fq challenges to be wrong.

### The Fix Required

Need to implement **Fq Poseidon** in Go with the correct parameters from `poseidon_fq_params.rs`:
1. Different MDS matrix (4x4)
2. Different round constants (256 values)
3. Same structure (width=4, 8 full rounds, 56 partial rounds, alpha=5)

## Why This Wasn't a Problem in Manual Recursion (`feat/e2e-manual-recursion`)

The **manual recursion approach** handles this differently:

### Manual Approach (Working)
```
                    Outside Circuit (Rust)                 Inside Circuit (Gnark)
                    ──────────────────────                 ─────────────────────
┌─────────────────────────────────────────┐     ┌──────────────────────────────────┐
│  1. Derive challenges from Fq Poseidon  │     │  1. Receive L, R, U as public    │
│  2. Compute L = eq(·, z_L)              │ ──▶ │     inputs                       │
│  3. Compute R = eq(·, z_R)              │     │  2. Verify MSM: C' = Σ L·C_i     │
│  4. Compute U = L^T · F                 │     │  3. Verify MSM: Com(U) == C'     │
│                                         │     │  4. Verify dot: <U, R> == v      │
└─────────────────────────────────────────┘     └──────────────────────────────────┘
```

- L, R vectors computed **outside** the circuit using real Fq Poseidon
- Passed as **public inputs** to gnark circuit
- Circuit only verifies commitments, no transcript needed

### Transpiled Approach (Failing)
```
                         Inside Circuit (Gnark)
                         ─────────────────────
┌────────────────────────────────────────────────────────────────┐
│  1. Derive challenges from Poseidon ← USES FR PARAMS, WRONG!  │
│  2. Compute L = eq(·, z_L) with wrong challenges              │
│  3. Compute R = eq(·, z_R) with wrong challenges              │
│  4. Sumcheck verification with wrong eq evaluations           │
└────────────────────────────────────────────────────────────────┘
```

- Recursion sumcheck runs **inside** the circuit
- Requires Poseidon hash with Fq parameters
- We only have Fr Poseidon → **all challenges are wrong**

### Options to Fix

1. **Implement Fq Poseidon in Go**: Add `poseidon_fq.go` with FQ_MDS and FQ_ROUND_CONSTANTS
   - Pros: Full transpilation, matches Rust exactly
   - Cons: Adds ~256 round constants, more circuit complexity

2. **Hybrid approach**: Use manual approach for recursion, transpile Fr stages
   - Pros: Already working in manual branch
   - Cons: Less elegant, two verification paths

3. **Change Rust to use Fr Poseidon for recursion transcript**:
   - Pros: No Go changes needed
   - Cons: Requires Rust changes, may affect security analysis

## Implementation Complexity Analysis

### Fr vs Fq Poseidon Implementations

The existing Go code uses **circom-optimized Poseidon** for Fr:
- Sparse matrix representation for partial rounds
- `cConstants` (88 values), `sConstants` (392 values), `mMatrix`, `pMatrix`
- Different algorithm structure from standard Poseidon

The Rust Fq uses **standard Poseidon** via `light_poseidon`:
- Simple round constants: 256 values (64 rounds × 4 elements)
- Standard MDS matrix: 4×4 = 16 values
- Standard algorithm: ark → sbox → mix for each round

### Implementation Options

**Option 1: Port standard Poseidon to Go (RECOMMENDED)**
- ~50 lines of algorithm code
- Copy 256 round constants + 16 MDS values from `poseidon_fq_params.rs`
- Create `poseidon_fq.go` with `HashFq()` function

**Option 2: Convert Fq to circom format**
- Would require poseidon-paramgen to generate optimized constants
- Complex and error-prone

### Standard Poseidon Algorithm

```go
func (c *FqPoseidon) Hash(state [4]Variable) [4]Variable {
    // First half of full rounds
    for r := 0; r < fullRounds/2; r++ {
        state = c.addRoundConstants(state, r*4)
        state = c.sbox5All(state)
        state = c.mdsMultiply(state)
    }
    // Partial rounds
    for r := fullRounds/2; r < fullRounds/2+partialRounds; r++ {
        state = c.addRoundConstants(state, r*4)
        state[0] = c.sbox5(state[0])  // Only first element
        state = c.mdsMultiply(state)
    }
    // Second half of full rounds
    for r := fullRounds/2+partialRounds; r < fullRounds+partialRounds; r++ {
        state = c.addRoundConstants(state, r*4)
        state = c.sbox5All(state)
        state = c.mdsMultiply(state)
    }
    return state
}
```
